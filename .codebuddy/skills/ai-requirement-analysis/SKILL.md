# AI 需求分析与数据集生成

## Overview

本 Skill 基于《AI 测试方法体系手册》，把需求转化为覆盖各评测维度的测试数据集。**不绑定任何具体系统**，通过数据源注入适配任意 AI 系统。

- **框架**：`ai-test-framework/`
- **维度表**：`ai-test-framework/dimensions/*.yaml`（A-E 五类，严格对齐手册）
- **Rubric**：`ai-test-framework/rubric/`（5 分制 + 阈值 + 统计）
- **生成脚本**：`ai-test-framework/scripts/_02_generate_dataset.py`
- **维护入口**：`ai-test-framework/scripts/_10_maintain.py`（regen / validate / review / install / export / selftest）

## 第一步：判断需求类型

| 类型 | 名称 | 维度数 | 判断依据 |
|---|---|---|---|
| **A** | MCP 工具 | 8 | 被测对象是纯 MCP 工具/接口 |
| **B** | Agent 系统 | 11 | 被测对象是对话 Agent（无外部工具） |
| **C** | Agent+MCP 集成 | 20 | **Agent 决策 + 真实 MCP 工具** ★ 最常见 |
| **D** | Skill 原子能力 | 6 | 测某个原子子能力 |
| **E** | RAG/知识库 | 5 | 文档检索增强生成 |

> 判断方法：先问"被测对象是什么"——纯接口→A；对话无工具→B；对话且背后调工具→C；单个子能力→D；文档检索→E。

## 第一步半：接入新 MCP（**遇到"MCP 交测"必做，且只用通用脚本**）

当被测对象是一个**新 MCP 端点**时，**第一步永远是先把它接进框架**，不要直接跳到生成数据集。

### 只用一条命令，禁止为每个 MCP 新建脚本

```powershell
cd ai-test-framework
python scripts/_01_mcp_setup.py --name <系统名> --url <MCP端点> \
    [--token <TOKEN>] [--company-id <ID>] [--company-header CompanyId] [--req-type C] [--dry-run]
```

它会自动完成：**拉全量工具 schema → 平铺 → 落盘 `results/mcp_schemas/<系统名>.json`
→ 落盘 `<系统名>.overview.md` 业务域概览 → 写 `.env` → 生成 `configs/<系统名>.yaml` 骨架**。

> ⛔ **铁律：不要为某个具体 MCP 写 `_probe_<系统>.py` 这类一次性脚本。**
> `_01_mcp_setup.py` 是「任意 MCP 通用」的接入器，新 MCP 永远复用它。
> 业务域分类等判断逻辑应**沉淀进 `_01_mcp_setup.py`**（见下），而非散落成一次性文件。
> 唯一的例外是**与具体 MCP 无关**的「中文路径绕乱码」辅助（见本文件末「Windows 中文路径」）。

### 脚本自动识别「参数外壳」，勿手工判断

不同 MCP 把入参包在不同外壳里，`_01_mcp_setup.py` 会自动探测并写进 config 的 `参数包装`：

| 外壳形态 | 代表系统 | config 的 `参数包装` |
|---|---|---|
| `properties.toolParams` 内层才是真参数 | POS / 小韩面 / AutoMart / RetailPOS | `toolParams` |
| `properties.parameters` 内层才是真参数 | PocketStore | `parameters` |
| properties 直接是参数 | 少数简单 MCP | 不写（executor 回退 `toolParams`） |

`generic_mcp_executor` / `direct_mcp_executor` 会读 `参数包装` 把入参包对应一层——
**若执行时全部报「参数缺失/校验失败」，首先核查 config 的 `参数包装` 是否与该 MCP 一致**。

### 接入后立刻看三件事（决定后续测试范围）

1. **`<系统名>.overview.md`**：工具总数 + 业务域分布 + 每个工具的**真实必填参数**。
2. **读/写比例**：若绝大多数是写操作（改价/删除/批量），必须走「写入安全边界」维度（见下），
   且执行前确认是**隔离测试环境**。
3. **鉴权语义**：部分 MCP `list_tools` 免鉴权但 `call_tool` 要 token（如 PocketStore 报 `code=1002`）；
   部分工具的必填参数**不含店铺 ID**（直接按实体 ID 操作，如 `item_update` 只要 `itemId`）——
   这类是高危写入面，测试时尤其注意影响范围。

### 前置条件自检（接入完就能填）

| 数据源 | 是否必须 | 影响 |
|---|---|---|
| **能力目录** | ✅ **必须** | 系统有哪些操作/查询能力。没有它，只能按维度表生成通用骨架，**与被测系统无关，无意义** |
| **真实实体清单** | ⚠️ **建议（可降级）** | 真实的商品/点位/对象。有 → 用例真实、verify 可落地；无 → 先生成结构骨架，后续接真实数据补齐 |

- 能力目录没有 → **要求用户提供**该系统的能力清单（否则拒绝继续，产物无效）
- 实体清单没有 → **可降级**：先用占位符生成结构骨架，明确告知"执行阶段需接入真实数据"

## 第一步¾：生成前「准入体检」（**强制，缺一不可**）

> 血的教训（PocketStore 2026-10-08）：首轮干跑 685 条，147 条失分**全是数据集问题**
> ——假 ID / 枚举跨工具污染 / 必填参数漏生成 / 「实体不存在」被误归因 AI 系统。
> 根因是**没有在生成前做体检**，带着病数据集跑完才发现。以下四项**生成前必须自检**，
> 任一不通过就先修数据源，**不要往下生成**。

### ① 实体清单必须是「实调 MCP 拉到的真实 ID」

```powershell
# 用真实 token 调用列表类工具（如 item_list / category_list / menu_list），
# 把返回的真实 ID 写进 实体清单_<系统>.yaml，禁止从 schema 快照抄/编造 ID。
```

- ⛔ **禁止用占位/编造 ID**（`'0'`、全 9、连续数字）做「正常执行」用例 —— 服务端会返回
  `data is null` / `not found`，导致用例必然失败，且**结果只能看到"系统报错"，看不出是数据集问题**。
- ⛔ **禁止从 `results/mcp_schemas/*.json` 抄 ID** —— 那里只有 schema（字段定义），没有真实数据 ID。

### ② 枚举取值必须「按工具」核对，不能全局一刀切

- 同名参数（`status`/`type`/`mode`）**在不同工具下语义不同**：如 `status` 在
  「商品上下架」是 `OnSale/OffSale`、在「店铺营业」是 `open/closed`、在 `item_update` 甚至**是整数**。
- 优先让生成器**从参数 description 自动提取**（很多 MCP 把合法值写在描述里，如
  `mode: "Sales mode: 'regular' ... 'fixed_date' ..."` → 自动得到 `regular`/`fixed_date`）。
- config 必须用**按工具细化**写法，禁止全局：
  ```yaml
  param_enums:
    status:                       # 全局会污染所有叫 status 的参数
      - {tools: [batch_item_status], values: [OnSale, OffSale]}
      - {tools: [set_store_open_status], values: [open, closed]}
  ```

### ③ 能力目录的参数必须逐条对齐工具 schema 的 required

- 打开 `configs/<系统>.yaml` 的 `mcp_tools`，逐工具核对 `required`；
  能力目录的 `参数:` **至少覆盖必填**（生成器会自动补 + 告警，但**根上要对齐**）。
- ⚠ 注意「二选一」必填（如 `batch_item_price` 要 `merchFoodIds` **或** `merchId+categoryId`）——
  能力目录要写清，否则必填只是"其一"。

### ④ 生成后必跑硬校验门禁，**FAIL 就不准往下走**

```powershell
python scripts/_10_maintain.py validate <系统>   # 必须在 regen 之后、执行之前跑
```

校验器会硬拦三类「期望成功但不可能成功」的用例（缺必填 / 枚举非法 / 占位 ID），
报错文案会指明**该补参数还是该换真值**（**不是**改 block=true）。
**只有 `结论: PASS` 才能进入执行阶段。**

### ⑤ 先干跑一轮，且**先自查归因**再出报告

- 若被测 MCP 带 `confirm` 二段式，用 `CONFIRM_DRYRUN=1` 零风险跑一轮。
- **看到失分先问"是数据问题还是系统问题"**：已知会被判「数据集问题」的特征包括
  `data is null` / `not found` / `缺必填` / `枚举非法` —— 这些**不是系统的错**，
  不要直接当「AI 系统缺陷」提给开发。

## 第一步⅞：形态体检 —— 提前判断「这次会不会需要扩展框架」

> 目的：**不要等跑完一轮才发现框架扛不住**。接入后立刻看
> `results/mcp_schemas/<系统>.overview.md` 顶部的「形态信号」一行
> （由 `_01_mcp_setup.py` 自动扫描工具 schema 生成，无需手工分析）。

### 怎么用

打开 `<系统>.overview.md`，看是否有 ⚠ 形态信号，对照下表决定"能不能直接用现有框架"：

| 形态信号 | 现有框架是否支持 | 若命中要做什么 |
|---|---|---|
| **未发现特殊形态** | ✅ 直接可用 | 照常生成/执行，无需扩展 |
| **分页游标**（cursor/pageToken/offset） | ⚠ 部分是 offset 能当普通参数；**纯 cursor 链式翻页**不支持 | 先小样本验证；若需翻页，评估是否扩展执行器 |
| **嵌套参数**（object / array-of-object） | ⚠ 单层嵌套（如 `products: [{...}]`）可生成；**多层嵌套**需人工确认结构 | 检查生成的 `tool_params` 结构是否合法 |
| **数组参数**（批量语义） | ✅ 支持（生成器会给单元素数组） | 注意元素结构是否符合 schema 的 `items` |
| **整数时间戳**（epoch） | ⚠ 生成器默认给 ISO 字符串，**可能不匹配** | 在能力目录/config 里声明该参数的真实格式 |
| **参数外壳**非 toolParams/parameters | ⚠ 需人工 | 把外壳名加进 `_01_mcp_setup.py` 的 `KNOWN_WRAPPERS` |
| **鉴权**非单 Bearer（双 token/OAuth/签名） | ❌ 不支持 | 需扩展 executor 鉴权逻辑，或先用静态 token |

### 判定原则

- **命中 ✅ 行** → 放心往下走，这是常规系统。
- **命中 ⚠ 行** → 先做**小样本验证**（挑 3~5 条相关工具的用例手工跑），确认能生成出合法参数；不能则按"要做什么"列处理。
- **命中 ❌ 行** → **先扩展框架再生成**，否则一定是白跑。

> 记住：**框架代码稳定、新系统靠配置适配**。绝大多数新 MCP 都是 ✅ 行，
> 只有出现上表 ⚠/❌ 的**新形态**时才动框架——而现在这些形态会被**提前列出**，
> 不再是"跑完才发现"。

## 第二步：前置条件（生成前必读）

**接需求后，第一步不是生成，而是先确认被测系统的数据源**，缺了它生成的用例跟系统无关：

| 数据源 | 是否必须 | 影响 |
|---|---|---|
| **能力目录** | ✅ **必须** | 系统有哪些操作/查询能力。没有它，只能按维度表生成通用骨架，**与被测系统无关，无意义** |
| **真实实体清单** | ⚠️ **建议（可降级）** | 真实的商品/点位/对象。有 → 用例真实、verify 可落地；无 → 先生成结构骨架，后续接真实数据补齐 |

**操作指引**：
- 能力目录没有 → **要求用户提供**该系统的能力清单（否则拒绝继续，产物无效）
- 实体清单没有 → **可降级**：先用占位符生成结构骨架，明确告知"执行阶段需接入真实数据"

## 第三步：测试集分层架构（L1/L2/L3）

按手册要求数据集分三层，当前实现 L1/L2，L3 生产回放暂不接入：

| 层 | 名称 | 占比 | 用途 | 生成方式 |
|---|---|---|---|---|
| **L1** | 黄金集 | 60% | 覆盖全部能力 × 全部维度，质量最高、最稳定 | **按手册维度驱动**（`build_l1` 遍历维度表，每维度按核心测试方法生成；A/D→build_a/build_d，E→build_e） |
| **L2** | 场景演化 | 30% | 实体替换 / 数值变异 / 表达改写 / 注入对抗 | 纯规则变异（**不用 LLM**） |
| **L3** | 生产回放 | 10% | 真实生产 trace 采样 | 暂不接入、不预留接口 |

> **为什么不用 LLM 生成**：LLM 生成 JSON 截断、ID 重复、verify 字段不规范，不稳固。当前 L1 按维度规则模板、L2 用确定性变异，可复现、可回溯。
>
> **评分也优先确定性规则**：能规则化的维度（意图/返回/参数/结构）用「确定性语义校验器」自动评分（免费/稳定/可解释），只有真主观的维度（上下文贴合度/规划合理性）才用 LLM-as-Judge。

## 第四步：通用化（适配多系统）

生成脚本通过参数注入数据源，**同一脚本可给任意系统复用**：

- **能力目录**：`--ability <能力目录.yaml>` 注入被测系统的能力清单
- **真实业务实体**：`--products <实体清单.yaml>` 注入真实对象清单（不虚构）
- **系统名**：从能力目录 yaml 的元信息读取，避免命令行中文乱码
- **能力目录自动发现**：脚本自动扫描 `ai-test-framework/ability/` 下所有 yaml

### 能力目录的 Task 结构（通用、跨系统）

能力目录是**系统相关的"数据"**，需按业界 Task 结构声明，生成脚本自动消费、**不绑定具体系统**：

| 字段 | 含义 | 作用 |
|---|---|---|
| `能力` | 能力名 | 生成用例的能力字段 |
| `操作类型` | 查询/创建/变更数值/变更状态/删除/组合/人工 | 维度生成器**挑选代表能力**的辅助（如"改价/删除"作工具选择矩阵），生成自然话术 |
| `成功标准` | 怎么算"做对了"（Outcome） | **评分结果而非路径** |
| `参数` / `工具` | 该能力调用参数与工具 | 生成用例的 params/工具 |
| `负向场景` | 该能力**不应做**的操作 | 生成"平衡问题集"（应当 + 不应），防 AI 乱来 |
| `layer` | L1 回归 / L2 能力 / L3 压力 | 对齐业界 Capability/Regression 分层 |

**`成功标准` 三种模式**（校验"AI 是否真的做对"，不轻信 AI 的话）：

| 模式 | 校验方式 | 适用 |
|---|---|---|
| `db` | 操作后调**查询工具**取回真实状态，比对字段值 | 能查到底层状态的系统（改价→查价格） |
| `语义` | 看 AI 输出内容是否满足期望 | 无法查状态的系统（问答/检索） |
| `拒绝` | 该操作应被拦截，不能执行 | 负向场景（越权/注入） |

**`语义` 模式写自然语义期望即可**（如"返回含名称/价格/状态的列表"），生成脚本自动解析为可校验项（`fields`/`contains`）填进 `期望.semantic`，评分时由语义校验器自动评分——**系统作者无需懂校验细节**。

## 执行命令

```powershell
cd ai-test-framework

# 方式一（推荐）：维护入口一键 regen（自动发现能力目录/实体清单，产出 *.new.yaml）
python scripts/_10_maintain.py regen    <sys> [type...]   # sys = retailpos / unattended
python scripts/_10_maintain.py validate <sys> [type...]   # 硬校验（FAIL 则不许进执行）
python scripts/_10_maintain.py review   <sys> [type...]   # 软 review（人工扫一眼）
python scripts/_10_maintain.py install                     # 备份旧版并装正式版

# 方式二：直接调生成器（细粒度控制时用）
cd ai-test-framework/scripts
python _02_generate_dataset.py ^
  --req-type <A|B|C|D|E> ^
  --ability <能力目录.yaml> ^
  --products <实体清单.yaml> ^
  --out ../datasets/<类型>_<系统>.yaml

# 降级版：只传 req-type + system（自动发现能力目录，实体清单缺失时降级为结构骨架）
# 注意：Windows 终端直接传中文路径可能乱码，推荐用 --system 触发自动发现
python _02_generate_dataset.py --req-type <A|B|C|D|E> --system <系统名> --out ../datasets/<类型>_<系统>.yaml
```

参数说明：

| 参数 | 必填 | 说明 |
|---|---|---|
| `--req-type` | 是 | 需求类型 A/B/C/D/E |
| `--ability` | 是（建议传） | 能力目录 yaml 路径；不传则自动扫描 `ability/` |
| `--products` | 否（建议传） | 真实业务实体清单 yaml 路径；不传则自动匹配，找不到时降级为结构骨架 |
| `--out` | 是 | 输出数据集路径 |

## 数据集字段

每条用例包含：

| 字段 | 含义 |
|---|---|
| `用例ID` | 全局唯一，格式 `<类型>-<层>-<编号>` |
| `层` | L1 / L2 |
| `维度` | 评测维度（来自维度表） |
| `能力` | 被测能力（来自能力目录） |
| `输入` | 自然语言指令 |
| `期望` | 期望意图 + 参数 + 输出（含自动解析的 `semantic`） |
| `verify` | 操作后校验（`{field, expect}` 或 `None`） |
| `期望.semantic` | 从能力目录「成功标准:语义」自动解析的确定性校验项（`fields`/`contains`），供自动评分 |
| `标签` | 场景类型（正常/边界/异常/对抗/模糊/多轮），**不含层** |
| `sample_extra`（可选） | 该用例的额外采样次数（如非确定性与稳定性维度标 5 次），供 pass@k 重复跑 |

> **校验机制**：评分时优先用「确定性语义校验器」(`rubric/semantic_verify.py`) 自动评分
> （文本包含/字段齐全/值相等，不依赖 LLM，via=rule）；规则判不了的主观维度才下沉到 LLM-as-Judge。

## 生成后检查（**验收清单，必须逐项跑完**）

> **为什么这节是强制的**：生成器产出「矛盾用例 / 真重复 / 缺 semantic」不会报错，
> 但会在执行阶段浪费真实 MCP 调用，或让评分判不出来。
> 本清单的目的是**把问题暴露在执行之前**，不是事后补救。

### ① 硬校验（门禁，FAIL 不许进执行）

```powershell
python scripts/_10_maintain.py validate <sys> [type...]
```

判定：**PASS 才往下走**；FAIL 说明用例与能力目录矛盾（如引用不存在的工具），必须先修。

### ② 软 review（人工扫一眼，找"会白跑"的问题）

```powershell
python scripts/_10_maintain.py review <sys> [type...]
```

## 破坏性/写入类工具的安全测试（写入安全边界）

**背景教训（真实事故，2026-09-15）**：某 POS MCP 的 `delete_products_by_ids` 传入 1 个**不存在**的
`productId` 时，服务端**忽略过滤条件**、真实删除了账号下 **983** 个商品，并返回 `code=0`。

按原有「参数校验 / 安全与权限」维度，该用例会被判 **5 分**（系统"调用成功"），**缺陷完全漏网**。

**根因**：这类缺陷的行为特征不是"拒绝失败"，而是**「成功返回，但作用范围爆炸」**——
凡是以 `block=true`（期望系统拒绝）为断言的维度都抓不到。所以必须换断言方式。

**新增 A 类第 9 维「写入安全边界」（C 类自动继承），测试方法为「两级影响范围对账」**：

| 判据 | 步骤 | 断言 |
|---|---|---|
| ① **存在性对账**（主判据，不依赖基线）| 执行前用只读工具**按 ID 探「本次操作的真实目标实体」**（应存在）→ 执行（传不存在的 ID）→ 执行后再探一次 | 真实实体**一旦消失**即判 1 分：传的是不存在的 ID，却动了真实数据 |
| ② **总数对账**（辅判据）| 执行前用同实体域只读快照工具取总数 `before` → 执行 → 再取 `after` | `\|after − before\| ≤ 传入目标数`（本类为 0），超出即判 1 分 |

判定优先级：① 真实实体消失 → **1 分**；② 基线 > 0 → 按 Δ 判 5 / 1 分；③ 基线不可用但真实实体仍在 → **5 分**（有实证）；④ 两类证据都没有 → **不判分**（避假）。

> 为什么要主判据：快照工具可能被选成 `search_xxx_by_name` 这类需传名称的查询（取空串仍可能返回 0 条），
> 基线恒为 0 → 总数对账无法判定，用例等于"白测"。存在性对账只要测试环境有 ≥1 条真实数据就能判定，
> 且在本次事故场景（忽略过滤、删全量）下**必然命中**。

用例结构（`build_a` 自动产出，无需手写）：

```yaml
维度: "写入安全边界"
输入: {tool_name: delete_products_by_ids, tool_params: {productIds: ["0000000000000000"]}}
期望:
  block: false                # 不是期望「拒绝」，而是期望「成功但影响 0 条」
  影响范围对账:
    快照工具: query_products_by_filter     # ② 总数对账（辅）
    快照参数: {}
    最大影响条数: 0
    存在性检查:                             # ① 存在性对账（主）
      工具: query_products_by_ids           # 取能力目录「成功标准·模式 db」声明的校验工具
      参数: {productIds: ["9088145987535878"]}   # 真实 ID，来自实体清单
      目标ID: "9088145987535878"
  高危: true
高危: true                    # 执行器默认跳过，需 ALLOW_DESTRUCTIVE=1 才执行
```

**执行安全红线（必须遵守）**：

1. 该类用例自动标记 `高危: true`，**执行器默认跳过**；仅在确认是**隔离测试环境**后
   设置 `ALLOW_DESTRUCTIVE=1` 才会真正执行。
2. **禁止**在含真实数据的环境执行；**禁止**用"不存在的 ID"去试探破坏性接口
   （本次事故正是由此触发——过滤参数可能被忽略，退化为全量操作）。
3. 基线 `before = 0` **且存在性探针也没拿到证据**时不判分（无法证明范围受控），
   需人工确认，避免"Δ 恒为 0 → 恒满分"的假阳性；反之若真实目标实体探针存在、
   操作后仍在，则判 5 分（有实证，避免"全都不可判 → 白测"）。
4. 测写入类工具的正确姿势：**自己建 → 操作 → 删自己建的**，全链路隔离。

**生成时自动处理**：`build_a` 为每个「操作类型 ∈ {创建, 删除, 更新}」的能力自动生成该类用例：

- ① 存在性探针：优先取能力目录「成功标准 · `模式: db`」里声明的 `校验工具`
  （如 `query_products_by_ids`），参数用**实体清单里的真实 ID**（禁止用 0/1 等假值顶替）；
- ② 快照工具：按「同分组/同实体域 + 参数最少」自动挑选（尽量避免按条件过滤的
  `search_xxx_by_name` 导致基线恒为 0）；
- 没有可用探针时自动退化为「仅总数对账」，不会生成无法判定的用例。

**回归自测**：`python scripts/_10_maintain.py selftest`（**改完框架代码先跑这个**，离线、不连 MCP）。

## 附：Windows 中文路径导致脚本跑不起来时

若工作区路径含中文（如 `...\CodeBuddy\AI测试\...`），PowerShell 执行
`cd <中文路径>` / `python <中文路径>\scripts\xxx.py` 时中文可能被错误重编码成乱码
（`AI测试` → `AI娴嬭瘯`），报 `can't open file` / `找不到路径`。

**通用绕过方式（与具体 MCP 无关，可复用）**：不把中文路径写进命令行，改为在 Python 内
用 base64 解码出路径再执行：

```powershell
python -c "import base64, runpy, sys; sys.argv=['_01','--name','X','--url','...','--dry-run']; runpy.run_path(base64.b64decode('<路径的base64>').decode('utf-8'), run_name='__main__')"
```

> 生成 base64：`python -c "import base64;print(base64.b64encode(r'C:\...\scripts\_01_mcp_setup.py'.encode()).decode())"`
> 这是**环境适配**，不是「给某个 MCP 写脚本」——同一段命令对所有脚本、所有 MCP 通用。
